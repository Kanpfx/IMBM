SC2Arena / StarEvolve 论文与本项目组件对照

本文档对照论文 SC2Arena and StarEvolve: Benchmark and Self-Improvement Framework for LLMs in Complex Decision-Making Tasks 梳理当前项目的代码部件。结论先说清楚：当前仓库不是完整论文复现，而是从 SunTzu / IMBM 分支中裁剪出的 Terran-only IM/BM 运行时。它保留了 SC2Arena 的文本观测、JSON 动作、动作校验、动作执行、日志指标等核心闭环， 并把 StarEvolve 的 Planner-Executor-Verifier 思路改造成了“BM 后台战略指导 + IM 即时动作执行 + 代码 verifier 自修正”的轻量结构。

论文：arXiv:2508.10428 论文框架：SC2Arena + StarEvolve 当前项目：Terran IM/BM runtime 入口：main.py

阅读口径

论文介绍的 SC2Arena 是一个完整 StarCraft II LLM benchmark，强调全局游戏上下文、完整低层动作空间、三族支持、 agent-vs-agent 评估、文本观测优化和标准 JSON 接口。StarEvolve 则是在该 benchmark 上运行的层级式自改进框架， 由 Planner、Executor、Verifier、自修正以及高质量轨迹 SFT 组成。

当前项目只保留 IM/BM 流程：IM 负责同步决策并输出可执行 JSON action；BM 在后台异步生成高层 directive； DirectiveStore 是两者之间唯一共享通道。训练数据筛选、SFT、Elo 批量评测和三族完整支持不在当前主流程内。

整体运行链路

1. 启动配置 main.py 解析地图、难度、AI build、种族和 -bm 开关，并加载 IM/BM API 配置。
2. 创建对局 main.py 使用 python-sc2 创建 Bot(ImBmPlayer) 对战内置 Computer。
3. 文本观测 BasePlayer.obs_to_text() 把单位、建筑、能力、敌人、资源和动作历史转成 LLM 可读文本。
4. IM 决策 ImAgent 读取当前观测和有效 directive，输出 JSON actions 与是否请求 BM 更新。
5. 校验执行 verify_actions() 和 check_action() 做合法性检查，run_actions() 调用 SC2 ability。
6. BM 后台 BmAgent 被冷启动、过期或 IM 请求触发，异步写入新 Directive。

信息过载优化：单位聚合 units_to_text()、abilities_to_text() 正在自动采矿或自动攻击的 worker 会被合并成一组；拥有相同 ability 集合的单位会在 ability 文本中聚合。 这减少重复 token，让模型把注意力放在需要决策的单位和结构上。 已实现

指标与日志 logging()、log_current_iteration()、on_end()、runtime/metrics.py 运行中记录 minerals、vespene、supply、unit/structure value、可见敌人数量、IM/BM latency、actions、directive 等； 对局结束记录 result、SBR、time cost、RUR，并写入 trace.json。 保留部分论文指标

StarEvolve Executor agents/im.py IM 是当前唯一动作生成模型。它接收 observation 与 BM directive，直接输出低层 JSON actions。 因此当前 IM 同时包含“战术执行器”和“动作生成器”的职责。 改造成 IM

当前项目各文件的作用

main.py：对局入口

负责命令行参数、环境变量校验、IM/BM client 创建、玩家创建、config 日志写入和 run_game 启动。 普通运行只需要 IM 配置；加 -bm 时额外要求 BM 配置。

config/：静态配置

game.py 提供地图、难度、AI build、race choices。 env.py 负责 .env 加载、必填变量检查和 generation config。

core/player.py：IM/BM 调度器

ImBmPlayer.run() 是每次 SC2 step 的核心。它控制决策间隔、矿量门槛、directive 读取、IM 调用、动作执行和 BM 触发。 BM 使用 asyncio.create_task 异步运行，避免阻塞下一轮 IM 行动。

core/base_player.py：SC2 适配层

这个文件最大也最关键：它把 SC2 原生对象转成文本，把模型 JSON 转成 ability 调用，并负责日志、指标、ID 映射、能力表加载、 动作校验、建筑落点查找和动作历史维护。

core/economy.py：自动经济

自动分配 SCV 与 MULE，优先补气矿、处理空闲工人、把多余 gas worker 释放到可用池，并在气矿仍缺工时从更远矿点补调 worker。 这降低了 IM 需要处理的低频经济噪声。

agents/im.py：即时动作模型

生成 IM prompt，解析 JSON，维护多轮修正历史。它输出三样关键结果：actions、 request_background 和 background_reason。

agents/bm.py：后台战略模型

冻结一份游戏状态和 IM 已验证动作，生成 {"guidance": [...]}。 它只给方向，不直接执行，避免慢速战略推理阻塞实时动作。

agents/prompts.py：共享战略和规则

保存最终目标和 race-specific rules。当前虽然函数支持三族规则，但结合能力表看，主运行口径仍应按 Terran 理解。

runtime/directive.py：BM/IM 通道

Directive 封装 guidance、发布时间、过期时间和来源； DirectiveStore 用锁保护最新 directive，读操作返回副本，写操作采用 newer-wins。

runtime/llm.py：模型调用

使用 OpenAI-compatible SDK，支持 base URL 和 API key。调用失败会重试；需要 JSON 时会预解析代码块内 JSON。

runtime/format.py：文本解析工具

提供 extract_code() 从三反引号代码块取 JSON、construct_ordered_list() 生成规则列表、 constrcut_openai_qa() 构造多轮 OpenAI 消息历史。

knowledge/：动作知识库

TerranAbility.csv 决定哪些 Terran action 可被模型看到和执行；data.json 提供 ability target 等原始游戏知识。

IM/BM 与论文 Planner-Executor-Verifier 的关系

论文角色 当前对应物 关键差异
Planner：输出自然语言战略命令 BM：输出 JSON guidance 列表 BM 是异步的，不每次决策都运行；它不直接把计划拆成可执行命令，而是把高层建议写入 directive，让 IM 自行吸收。
Executor：把命令转成 JSON actions IM：从 observation + directive 直接转成 JSON actions 当前少了一层显式“plan list”。优点是流程短、延迟低；缺点是 IM 需要同时做局势理解和动作选择。
Planner Verifier：检查战略计划 BM 解析 fallback + directive TTL 当前没有 LLM 战略 verifier；BM 输出非法时降级为 baseline guidance，过期时重新生成。
Executor Verifier：检查动作 JSON verify_actions() / check_action() 这一块非常接近论文：代码确定性校验动作语法、参数、资源和可执行性，并把错误反馈给模型修正。
Self-improvement：轨迹评分 + SFT 运行日志和 trace，暂无训练闭环 当前项目可以产生训练素材，但没有实现论文里的评分函数、样本筛选和微调脚本主流程。

运行时每轮决策如何发生

  1. on_step() 调用 ImBmPlayer.run(iteration)。
  2. _auto_micro() 先做 worker/MULE 分配和近身自动攻击。
  3. 如果不是决策 tick，只按间隔记录日志后返回。
  4. 如果矿量低于 decision_minerals = 50，跳过 LLM 决策，避免过早无效请求。
  5. 生成 obs_text，读取当前有效 directive。
  6. 调用 ImAgent.run(obs_text, directive, verifier=self.verify_actions)。
  7. IM 输出 JSON；如果 schema 错或动作非法，IM 根据错误反馈最多重试 3 次。
  8. run_actions(actions) 执行动作并更新 action history。
  9. 如果 IM 请求 BM、没有 directive、或 directive 过期，则启动后台 BM 任务。
  10. BM 完成后写入 DirectiveStore，下一轮 IM 决策读取。

与论文完整实现的边界

边界 当前状态 影响
三族完整动作空间 当前只可靠支持 Terran。 可以用于 Terran IM/BM 实验，但不能声称完整复现 SC2Arena 三族 benchmark。
显式 Planner/Executor 双阶段 BM/IM 替代双阶段，但中间没有自然语言 plan list。 更适合实时运行与工程简化，但与论文 StarEvolve 结构不完全等价。
LLM Planner Verifier 当前没有独立战略 verifier。 BM guidance 质量主要靠模型本身和 TTL 刷新，而非规则化战略校验。
SFT 自改进 日志足够作为数据来源，但未实现评分筛选和训练闭环。 当前项目是 runtime，不是完整 self-improvement pipeline。
Elo 与批量评测 旧脚本归档。 单局运行可用；论文式系统评测需要额外恢复或重写 eval 模块。

如果后续要继续贴近论文，可以补哪些模块

  • eval/：围绕当前 main.py 做批量 map/difficulty/model 评测，重新计算 WR、TCW、SBR、RUR、VAR、TPD 和 Elo。
  • training/：从 logs/ 抽取 IM/BM prompt-response、动作有效性和最终胜负，形成 SFT 数据。
  • agents/verifier.py：在代码 verifier 外加一个可选 LLM strategic verifier，用于检查 BM guidance 或显式 plan。
  • knowledge/ProtossAbility.csv / ZergAbility.csv：补齐三族动作表，才能向论文完整 SC2Arena 靠齐。
  • runtime/clock.py：统一 iteration、game_loop 和 directive TTL 的时间语义，减少异步调度歧义。
