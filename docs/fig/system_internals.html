IMBM 内置架构细节说明

参照 架构细节.md 与当前代码实现整理。页面重点解释系统内部默认逻辑：自动控制、建议系统、知识库、状态压缩、决策触发、IM/BM 异步关系、verifier 与动作执行。

核心定位

当前主程序使用 ImBmPlayer。它保留 SunTzu 的自动经济、自动微操、状态压缩、动作校验和执行层；在决策层上，用同步阻塞的 IM 代替旧 action path，用可选异步 BM 代替后台战略建议来源。

一句话数据流

on_step 先执行自动逻辑，再在决策点构造观测；IM 同步生成动作并通过 verifier 修正；动作落地后再按需触发 BM，BM 后台写入 DirectiveStore 给之后的 IM 使用。

运行主循环

1

on_step

只要己方单位和基地存在，就进入 run(iteration)；每 15 iteration 更新一次生命值缓存。

2

自动逻辑

先执行工人/MULE/自动还击/SCV 防守等无需 LLM 的即时控制。

3

决策触发

默认 iteration % 30 == 0 且矿物至少 170，或到达强制触发点。

4

IM/BM

IM 当前轮同步产出动作；BM 只在后台异步刷新指令，不阻塞当前动作执行。

自动部分

自动工人分配

  • 入口是 distribute_workers()。
  • 按基地附近矿点和气矿统计需求。
  • 优先补 gas 缺工，再把剩余 idle worker 派往矿点。
  • 会释放 gas surplus worker 进入可重新分配池。

MULE 自动采矿

  • Terran 分支调用 _deploy_mules()。
  • 按资源量、距离、当前采集单位数量、已有 MULE 数计算矿点分数。
  • 只对 idle MULE 自动下采矿命令。

全单位自动还击

  • 每轮遍历己方单位，跳过 MULE 和正在建造的 SCV。
  • 若敌人在当前单位攻击范围内，攻击生命值最低目标。
  • 该逻辑发生在 LLM 决策之前。

前期 SCV 防守

  • 当敌人靠近出生点且时间小于 240s 时，SCV 会自动攻击。
  • 防守半径由 scv_auto_attack_distance = 4 控制。
  • 目标同样选最低生命值敌人。

自动建筑落点修正

  • run_actions() 执行 build 类动作时，调用 find_placement() 搜索可放置位置。
  • Terran Barracks/Factory/Starport 会额外检查 addon 位置。
  • 这意味着 IM 给出的目标点不一定是最终建筑落点，执行层会尝试修正。

建议系统

建议由 get_suggestions() 生成。当前 IMBM 主路径中，这些建议不是追加给同步 planner，而是在 BM 后台运行时追加进 BM 的规则集合。

类别 当前逻辑 作用
全局敌情 发现非工人敌军时建议攻击；60-300 秒提醒 3:00 敌军猛攻；300 秒后军队人口大于 15 且敌军较少时建议主动搜索消灭敌人。 把早期防守和中后期终结意识注入 BM。
资源使用 矿物大于等于 500 时建议消费、扩张或发展科技。 抑制资源闲置。
Terran build-up 补 Supply Depot、Refinery、Barracks、Tech Lab、Marine/Marauder、Factory、Siege Tank、Orbital Command、二矿、MULE。 用规则化提示补足 LLM 对开局节奏的稳定性。
其他种族 代码中也实现了 Protoss/Zerg 的 Pylon/Gateway/Queen/Inject/Overlord 等建议。 不只 Terran，但当前能力知识库以 TerranAbility 为核心，跨种族仍需注意。

知识库与能力表

knowledge/TerranAbility.csv

  • 提供 action 名、是否启用、自然语言描述。
  • get_ability_desc() 只把当前观测中出现且 enabled 的能力写入 prompt。
  • check_action() 用它判断 action 是否已知。

knowledge/data.json

  • 用于查能力目标类型，如 None、Point、Unit、PointOrUnit。
  • 动作字段校验依赖 target type 决定需要 target_position 还是 target_unit。

静态科技树

你的 md 中提到静态科技树“没用到”。从当前主链路看，主要确实依赖 CSV 和 data.json，未看到静态科技树进入 IM/BM 决策或动作校验路径。

状态压缩

观测结构

  • # Round state：时间、种族、矿气、军队/工人人口、剩余人口、地图尺寸。
  • # Own units / structures：己方单位和建筑摘要。
  • # Unit abilities / Structure abilities：可用能力摘要。
  • # Visible enemy units / structures：可见敌方信息。
  • # Action history：最近 10 个有效动作。

压缩技巧

  • 采矿工人聚合为一行，减少重复单位文本。
  • 单位按距离出生点的空间顺序排序。
  • ID 使用 tag % 1000 并处理冲突，降低 token 成本。
  • 能力按单位类型和能力集合聚合。
  • 矿点取和工人数相关的最近部分，气矿最多取 10 个。

动态状态检测

tag_to_health 每 15 iteration 更新一次。若当前生命值低于缓存生命值，单位状态会标记为 under attack。这是一种轻量“正在受攻击”检测，目前没有扩展到全部动态变化。

IM/BM 与 verifier

部件 当前实现 重要细节
IM Agent 同步阻塞调用 IM LLM，输出预测观测、动作、是否请求 BM、请求原因。 当前主路径显式传入 verifier=self.verify_actions，不是裸动作生成。
IM schema 修正 如果 JSON 缺字段、格式不对、预测观测缺 10 个 section，会要求 IM 重新输出。 当前本地最大重试次数为 2。
IM action verifier 动作校验失败时，错误信息会回传给 IM 让它修正。 这修正了 md 中“动作校验没传回错误信息”的旧描述；执行阶段失败仍只写日志。
BM Agent 后台通过 asyncio.create_task 启动，并用 run_in_executor 包住阻塞式 LLM 调用。 BM 不直接执行动作，只产出自然语言计划。
BM planner verifier BM 生成 plan 后调用 critic/refine 自审流程。 当前本地最大自纠错轮数为 2。
DirectiveStore 线程安全 latest directive 单槽，BM 写入，IM 在后续决策点读取。 不是队列；TTL 为 360 iteration。

动作校验与执行

verify_actions()

  • 检查 actions 必须是 list。
  • 逐个调用 check_action()。
  • 累加矿物、气体、人口成本，判断总资源是否足够。
  • 返回 ok, message，message 可回传给 IM 修正。

check_action()

  • 校验 action 字段、target 类型、unit id 是否存在。
  • 校验单位是否己方、是否具备对应能力、是否正在建造。
  • 校验资源、人口和供给建筑抑制规则。
  • Protoss Pylon 额外检查距离已有 Pylon 是否过近。

当前仍需注意

md 中写到“没验证重复 unit 使用”基本仍成立：IM prompt 规则要求同一个单位最多使用一次，但 verify_actions() 本身没有全局检查同一 unit id 是否在多个 action 中重复出现。

对 md 的关键修正

  • 10tick 已不是当前固定决策间隔；现在默认是 30 iteration。
  • 后续强制触发不是 90，而是 9 * 30 = 270 iteration。
  • 当前 IMBM 主路径不是旧同步 planner + action，而是 IM 同步动作，BM 异步计划。
  • planner/BM 自审和 IM 修正当前本地都是最多 2，而非 3。
  • 动作校验错误会回传给 IM 修正；但执行阶段错误不再即时回传。

当前限制

  • BM 使用当前真实观测；启用 -observation 时，IM 的 predicted_observation 仅用于记录/校验，不作为 BM 规划输入。
  • DirectiveStore 只有最新一条指令，没有历史队列或多版本计划。
  • 跨轮次记忆不是完全没有：有 directive、last_action、tag/id 映射、trace；但 LLM chat history 每轮重建。
  • 动作校验依赖当前可用能力与 TerranAbility 表，跨种族能力覆盖要谨慎。
  • 重复单位跨 action 使用主要靠 prompt 约束，不靠强校验。
